主观工程评分：**4.0/10**。该分数用于管理研发优先级，不是论文评分或安全等级。

## 3. 当前可用的核心实验基线

### 3.1 Mobilio 生产 D 冻结回放

同一组 481 帧的当前报告统计：

- 最终授权方向：49/481；
- 最终 UNKNOWN：275/481；
- GT danger 帧：295；
- 危险帧上仍出现方向指令：17/295；
- confirmed-clear 帧：150；
- confirmed-clear 上 STOP：0/150。

这些是**决策/授权统计**，不是独立的障碍物检测召回率。LEFT/RIGHT 是否真的避开障碍，还需要路径/轨迹真值。

理想输入 A 条件最终授权也只有 29/481。因此不能把当前低覆盖完全归因于 DAV2 或 VIO；地图搜索契约、Surface/Occupancy 证据和融合规则也需要检查。

### 3.2 E1 逐层矩阵

- Surface：CLEAR 79、OBSERVE 268、UNKNOWN 134；
- Occupancy：CLEAR 180、OBSERVE 35、UNKNOWN 266；
- Fusion UNKNOWN：275；

最终主因计数包括：

这些跨层原因不是可直接相加的互斥分母。必须保留逐帧和分层矩阵。

### 3.3 E2 Occupancy hint

随包独立复核支持：

最新 E3 任务书已经明确要求先验证旁路 trace 能捕获这些被筛掉的射线，再考虑 481 帧完整重放。**E3 完整回放尚未完成。**

## 4. 近期优先级：只推进一个主线

### E3：Surface 射线失败诊断

- 仅当输入、缓存、模型和标注都齐全时，才重放冻结 481 帧。

### P1：Basalt + TUM VI
- E3 诊断支线不代表 P1 通过。
- 只有实验环境、官方文件、MD5、许可、标定和 GT 均核验后，才开始一次单序列运行。
- 保存版本、命令、配置、日志、轨迹、有效帧比例、ATE/RPE 和失败记录。

### P2/P3：深度几何与地图

## 5. 强制停止条件

出现以下任一情况即 HOLD，不绕过：
1. 原始输入或必要缓存缺失；
2. 数据许可、来源或校验和不清楚；
3. 相机内参、时间戳、坐标系或尺度不一致；
4. trace ON 改变任何安全状态或授权结果；
5. 测试集被用于调参；
6. 指标分母、筛选条件或帧键不一致；
7. 只报告 UNKNOWN/hint/candidate 改善，却没有最终安全与可用性指标；
8. 需要删除用户文件、清理工作树或覆盖历史产物才能继续。

## 8. 每轮技术辅导与评分制度（长期执行）

用户要求每次阶段报告审查都同时提供技术选型建议、具体辅导和评分。该制度不得改变项目总方向：**PC-first、先复用成熟资源、先解决定位/几何/局部地图证据，手机验证最后；Last10m 独立验收；安全授权逻辑不因追求覆盖率而放宽。**

### 每次审查必须交付

1. **本轮结论：** GO / ADJUST / HOLD / STOP，并说明哪些证据支持该结论。
2. **技术选型：** 对当前瓶颈给出首选、备选和不建议采用的方案；解释收益、成本、数据要求、许可证/部署风险。只有新证据足以推翻旧选择时才改变选型，不为追新而换模型。
3. **技术辅导：** 解释失败发生在哪一层、如何定位、最小实验如何设计、如何复现；给出可执行步骤和必要命令。
4. **下一阶段提示词：** 每次只提供一个最小可证伪任务，明确输入、冻结项、输出、验收标准和禁止事项；如适合执行，写入 `docs/phase_prompts/`。
5. **仓库反馈：** 有实质新证据时，新增日期化审查记录并更新状态索引；没有实质变化时不制造空提交。
6. **进度评分：** 每轮都给出项目总分、各维度分数、阶段门禁状态，以及相对上一次的变化原因。

### 固定评分卡（0–10）

| 维度 | 权重 | 评分依据 |
|---|---:|---|
| 架构与模块边界 | 10% | 责任分离、接口契约、可替换性 |
| 感知能力 | 10% | 独立标注集上的类别/可行走区域表现 |
| 定位与时序融合 | 15% | 可复现 VIO/VO、ATE/RPE、跟踪和恢复 |
| 深度与三维几何 | 20% | 有真值的公制深度、地面法线、障碍物空间误差 |
| 地图与导航可用性 | 15% | Surface/Occupancy 一致性、可用覆盖、恢复能力 |
| 安全证据 | 20% | 危险漏放、误停、方向路径真值、失败安全性和独立验证 |
| 实验可复现性 | 10% | 数据/代码哈希、环境、命令、日志、分母、独立复算 |

总分按权重计算，保留一位小数。另报告：
- **技术选型成熟度**（是否已选定、是否已在桌面复现、是否已集成）；
- **阶段完成度**（按 P0–P6 门禁，不按提交/文件数量）；
- **证据等级**（DATASET / DESKTOP_REPLAY / PROTOTYPE / DEVICE_VERIFIED / USER_STUDY）。

### 评分纪律

- 没有实际运行证据的技术，不能因“选型已完成”获得运行分。
- 代码级单测不能算完整数据集回放；CSV 重算不能算重新运行模型；PC 结果不能算真机结果。
- UNKNOWN、observation_hint 或 surface candidate 增加，不自动算导航改善。
- 安全维度不得仅凭低漏放率评分；必须同时看误停、授权覆盖、方向是否真正避险和独立场景表现。
- 只有可复现的新证据才加分；发现数字错误、数据泄漏、授权语义回归或无法复现时应扣分或维持原分。
- 每轮写明相较上次的分数变化及具体证据，避免评分漂移。

**大方向保持不变。技术建议可以因证据调整，项目目标、PC-first 顺序和安全底线不能因短期指标波动而改变。**


## 9. 研发效率政策：减少低价值冒烟测试，增加技术验证投入

用户明确反馈：项目把过多时间花在重复冒烟测试、环境检查和形式化验收上，而不是提升核心技术；虽然不断寻找和复用开源项目，实际效果仍然很差。自本节生效后，所有执行任务必须遵守以下政策。

### 9.1 先区分测试类型，不能把所有验证都叫“冒烟测试”

- **冒烟测试（smoke）：** 只回答“本次构建/运行是否能启动关键路径”。每次有实质构建、依赖、接口或部署变化时运行一次最小集合即可。
- **单元/契约测试：** 只针对本轮修改的关键逻辑和安全不变量，保持快速、确定性。
- **基准实验（benchmark）：** 真正衡量技术能力，例如 Basalt 的 ATE/RPE、深度的 no-scale AbsRel/RMSE、地图的危险漏放/误停/覆盖率。这类实验是当前研发重点。
- **完整回归：** 只在阶段收尾、候选版本或明确高风险改动时运行，不要每次改一行文档或诊断字段都跑完整回归。
- **独立审计：** 用于核验数据和结果，不应反复重做已核验且输入未变化的步骤。

### 9.2 运行预算和触发规则

1. 不允许为了“证明还活着”重复运行同一 smoke suite。若代码、依赖、构建产物和环境没有变化，沿用最近一次通过记录。
2. 文档更新、报告整理、图表修订、提示词上传，不触发代码冒烟测试。
3. 纯诊断字段/日志字段改动：只运行相关单元/契约测试，以及一组 trace OFF/ON 决策等价检查；不自动重跑所有场景。
4. 核心算法、坐标变换、深度尺度、时间同步、地图更新或授权逻辑发生变化：运行对应定向测试，并执行一个能区分假设的基准实验。
5. 完整回归只在阶段门禁、发布候选或安全关键路径变更时运行。
6. 每轮报告必须记录测试耗时、实际发现的问题、测试覆盖的风险、是否重复；若连续三次只得到相同结果且输入/代码无实质变化，应停止重复测试并转向新的技术假设。
7. 原则上把执行资源优先给能产生新技术证据的实验；冒烟/重复检查只保留足以防止明显回归的最小集合。不得为了压缩时间而省略安全关键不变量测试。

### 9.3 复用项目必须通过“价值验证”，不是以接入成功为目标

引入 Basalt、Metric3D、NavAble、RTAB-Map 或其他开源项目时，必须先写清楚：
- 它要解决 BlindNav 的哪一个已量化瓶颈；
- 相对于当前基线的可证伪假设；
- 最小可运行数据与输入/标定要求；
- 对照基线和评价指标；
- 预期收益、计算成本、延迟/内存、许可证和适配成本；
- 若没有改善，什么条件下停止采用。

**克隆仓库、安装成功、模型能输出图片、测试全绿，都不等于技术能力提升。** 只有在相同数据、相同评估协议和独立 session 上，关键指标出现可重复改善，才考虑接入主链。

### 9.4 每轮工作必须有“技术产出”，不能只交测试清单

每个阶段任务的默认结构：
1. 先用最少检查确认输入、版本和实验可运行性；
2. 把主要时间用于本轮技术假设与对照实验；
3. 输出指标、失败案例、误差可视化和根因；
4. 给出 GO / ADJUST / HOLD / STOP；
5. 明确这轮新增了什么技术知识，以及下一轮只做哪一项。

如果因为缺少数据、磁盘、许可或依赖而无法进行有价值的技术实验，最多完成一次有针对性的阻塞诊断，然后停止重复检查，报告需要用户提供的唯一条件。不得用连续小型 smoke/test 报告伪装成项目进展。

### 9.5 对 BlindNav 当前工作的直接调整

- E3：只做一次最小 trace 预检与决策等价检查；通过后直接进行可用数据上的完整诊断回放。若原始输入缺失，立刻 HOLD，不反复跑空流程。
- Basalt：环境/文件校验只做一次；门禁通过后优先把时间花在 TUM VI 的 VIO 轨迹与 ATE/RPE 上，而不是反复打印依赖状态。
- DAV2：复用既有 57 帧结果，不重复跑相同推理。
- Metric3D：只有权重许可、焦距/尺度和小子集 GT 可验证时才运行一次有意义的对照；不为“装好模型”而装模型。
- Harvard/Mobilio：不做无假设的阈值扫描；每次改动必须对应一个已定位的失败原因，并同时报告安全性与可用性。
- 手机：继续最后，不因 PC 测试拖延而提前开始设备适配。

### 9.6 参考依据

测试层级应按风险和诊断价值选择：快速、窄范围的单元/契约测试作为基础，少量集成测试验证接口，昂贵且易脆弱的端到端测试只覆盖关键路径；不能用测试数量代替有效信心。参考：[Home Office Test Pyramid](https://engineering.homeoffice.gov.uk/standards/test-pyramid/)、[Martin Fowler Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)、[Software Engineering at Google](https://raw.githubusercontent.com/abseil/abseil.github.io/cd13b21daa6ec74155548241241693198c1b1264/resources/swe_at_google.2.pdf)。

**本政策的目标不是“少测试”，而是停止低价值重复测试，把时间转回定位、几何、地图和真实导航能力的量化改善。**

## 11. 技术反馈的主动纠错与提醒责任

用户要求：当用户或执行者提交反馈、实验解释或技术建议时，审查者不能为了顺从而默认同意。若发现事实、计算、算法理解、实验设计或结论有问题，必须主动、及时、明确地纠正；若问题复杂，则必须给出有技术依据的解释和替代方案。

### 11.1 必须主动核验的内容

对每份新报告/反馈，至少核对：
- 事实：仓库文件、代码行为、数据来源、版本和许可证是否支持该说法；
- 计算：分子、分母、筛选条件、单位、帧键、session 汇总是否正确；
- 算法：坐标系、尺度、时间同步、状态转换、射线/地图语义是否理解正确；
- 实验：对照是否公平、是否控制变量、是否存在数据泄漏、是否把相关帧当独立样本；
- 结论：证据是否足以支持“改善”“复现”“可部署”“安全”等措辞；
- 工程：复用组件是否真的带来可重复收益，还是只完成安装、接口或演示。

### 11.2 反馈有问题时的处理方式

不能只说“有问题”。必须给出：
1. **原反馈的具体主张**；
2. **问题类型**：事实错误 / 算术错误 / 术语混淆 / 逻辑跳跃 / 证据不足 / 方案不适配；
3. **可核查证据**：文件、代码行/函数、原始数据、官方文档或可复算指标；
4. **正确解释**；
5. **对项目决策的影响**；
6. **最小纠正实验或修改建议**；
7. **是否需要更正仓库报告/状态/提示词**。

复杂问题要解释关键机制和反例，不用一句“可能不对”带过。若证据不足以裁决，明确标记 DISPUTED / NOT_VERIFIED，列出能裁决的最小实验，不假装确定。

### 11.3 不盲从，也不为了反对而反对

- 用户/执行者反馈正确且证据充分：明确认可，并说明它改变了什么决策。
- 部分正确：保留正确部分，纠正错误部分。
- 错误：直接指出并给出依据。
- 新证据推翻旧结论：及时更新技术选型或评分，保留历史记录并解释为何改变。
- 不得为了维护自己以前的判断而忽略新证据。
- 技术路线大方向保持 PC-first、成熟复用优先、定位/几何/地图证据优先、手机最后；但具体技术选型允许被更强证据推翻。

### 11.4 及时提醒与时效责任

- 每次检查发现新报告、阶段门禁变化、关键技术错误、严重风险、用户需要批准的阻塞或可推进的 GO 时，应在同一轮向用户明确提醒，不只把信息写进仓库。
- 对会导致研发继续浪费时间的错误假设、重复测试、错误数据解释或无效复用，列为高优先级提醒。
- 对未变化且已提醒的阻塞不重复轰炸；只有出现新证据、状态变化或需要用户作决定时再次提醒。
- 如果自动检查没有产生用户可见通知，不得让用户误以为持续审查已经主动提醒；下次对话应说明最后检查时间和当前状态（若可查）。
- 不得承诺实时监控；当前自动审查按小时检查，外部系统/连接器不可用时必须如实说明。

### 11.5 每轮审查新增固定栏目

在原有反馈结构中增加：
- **我不同意/需要纠正的地方**：没有则明确写“本轮未发现需要纠正的关键主张”；
- **复杂技术解释**：说明核心机制、证据和反例；
- **及时提醒**：当前需要用户处理的事项及其阻塞影响；
- **技术辅导**：本轮最重要的原理/排查方法；
- **评分变化**：只根据新证据增减分，不根据讨论热度或文档数量变化。

**审查者的职责是保护项目免于错误结论和错误投入，不是迎合反馈。**
